== Context

The Aladin ecosystem is intended to support hundreds or thousands of independent knowledge domains.

An early design considered allowing every Knowledge Pack repository to operate its own API server and Docker container. Under that model, `aladin-kb-linux`, `aladin-kb-docker`, `aladin-kb-postgresql` and every other pack would become a separate active service.

Most Knowledge Packs primarily contain structured and relatively static knowledge. They do not require an independent permanently running server.

== Problem

A service-per-pack model would create unnecessary:

* memory and CPU overhead
* application processes
* network routes
* security boundaries
* health checks
* deployment configurations
* monitoring targets
* update procedures
* runtime dependencies

The architecture must support large numbers of packs while preserving independent development, reproducible releases, centralized retrieval, rollback, verification, horizontal scaling and offline operation.

== Decision

Aladin Knowledge Packs will be distributed as versioned data artifacts.

A Knowledge Pack repository is a source and build project. It is not required to operate as a permanent API service.

Each repository may contain:

* structured claims
* entities and relationships
* source and provenance records
* translations
* licensing metadata
* tests and evaluations
* schemas
* build configuration

A validation and build process converts repository content into one or more immutable Knowledge Pack artifacts.

Possible artifact formats include:

* SQLite
* JSON or JSON Lines
* Parquet
* graph data
* compressed archives
* search indexes
* optional embeddings

The exact mandatory formats will be defined by later specification documents.

== Architecture

[source,text]
----
Knowledge Repository
        │
        │ Validate
        ▼
Validated Source Data
        │
        │ Build
        ▼
Versioned Knowledge Artifact
        │
        │ Sign and publish
        ▼
Artifact Storage
        │
        │ Register
        ▼
Knowledge Pack Registry
        │
        │ Discover and load
        ▼
Gateway and Global Metadata Index
        │
        │ Retrieve and re-rank
        ▼
AI Runtime
----

== Runtime Model

A central gateway or compatible runtime may load many Knowledge Pack artifacts.

[source,text]
----
                 ┌── aladin-kb-linux artifact
                 ├── aladin-kb-bash artifact
Aladin Gateway ──┼── aladin-kb-docker artifact
                 ├── aladin-kb-postgresql artifact
                 └── additional Knowledge Packs
----

The gateway provides the active API layer. Multiple gateway instances may be deployed for horizontal scaling, high availability, regional distribution, local environments or private installations.

== Artifact Requirements

Every released Knowledge Pack artifact should include or reference:

* package identifier
* package version
* specification version
* creation timestamp
* source commit identifier
* content and artifact checksums
* build provenance
* licensing information
* compatibility metadata
* validation result
* source metadata
* maintainer identity

The specification may later require cryptographic signing for official or verified packages.

== Immutability

Released artifacts are immutable.

A published artifact must not be silently modified. Any content change requires a new package version.

[source,text]
----
aladin-kb-docker 1.2.0
aladin-kb-docker 1.2.1
aladin-kb-docker 1.3.0
----

Historical versions may remain available for reproducibility, auditability, rollback, compatibility testing and incident investigation.

== Safe Activation

A runtime should not immediately replace an active Knowledge Pack when a newer version becomes available.

. Discover the candidate version.
. Download the artifact.
. Verify checksums and signatures.
. Validate the manifest.
. Verify specification compatibility.
. Inspect package status and recall information.
. Build or update the search index.
. Run health and retrieval tests.
. Activate the new version atomically.
. Retain the previous version for rollback.

[source,text]
----
Active: 1.4.1
    │
    ▼
Download candidate: 1.4.2
    │
    ▼
Verify and validate
    │
    ▼
Build index and run checks
    │
    ▼
Atomic activation
    │
    ▼
Active: 1.4.2
----

If any required check fails, version `1.4.1` remains active.

== API Responsibility

Knowledge Pack repositories do not define independent production API deployments.

API responsibility belongs to:

* the Aladin Gateway
* compatible third-party runtimes
* local knowledge runtimes
* enterprise implementations
* development and validation tools

A repository may contain an optional temporary preview server, but this is not part of the required production architecture.

== Embeddings

Embeddings are derived artifacts. They must not replace the original structured knowledge.

Embedding metadata should include:

* model identifier and version
* vector dimensions
* normalization method
* chunking strategy
* generation timestamp
* source content hash
* language coverage

A runtime may ignore included embeddings and generate its own.

== Storage Independence

The specification will not require a mandatory storage provider.

Compatible implementations may use GitHub Releases, S3-compatible object storage, local file systems, private registries, distributed storage or enterprise artifact platforms.

== Security Consequences

Knowledge Packs are treated primarily as declarative data.

A compatible runtime must not automatically execute scripts contained in a pack. Artifacts remain untrusted until they pass integrity verification, schema validation, compatibility checks, resource limits, security scanning and policy checks.

== Positive Consequences

This decision provides:

* low runtime overhead
* centralized API management
* easier horizontal scaling
* reproducible releases
* safe rollback
* consistent security controls
* local and offline compatibility
* independent package development
* support for very large pack ecosystems

== Negative Consequences

The ecosystem additionally requires:

* artifact builders
* artifact storage
* a package registry
* gateway loading logic
* index synchronization
* compatibility adapters
* cache invalidation
* package lifecycle management

Knowledge Pack maintainers cannot deploy arbitrary custom server behavior as part of the core format.

== Alternatives Considered

=== One API Server per Knowledge Pack

Rejected because it creates excessive operational overhead and poor scaling characteristics.

=== One Large Monolithic Knowledge Repository

Rejected because it would reduce independent ownership, complicate licensing, create large merge conflicts and introduce a central failure point.

=== Direct Runtime Access to Git Repositories

Rejected as the primary production mechanism because repositories may contain incomplete, unvalidated, unsafe or unstable content.

=== Mandatory Central Cloud Service

Rejected because the public specification must remain usable locally, offline, self-hosted and through independent implementations.

== Compatibility

This decision applies to the first Aladin Knowledge Pack specification series.

Future versions may introduce optional services or extensions, but the core portable Knowledge Pack must remain usable as a data artifact.

== Implementation Guidance

The first reference implementation should prove this decision with at least two independent Knowledge Packs and demonstrate:

* artifact generation
* centralized loading
* unified multi-pack search
* package replacement without a gateway restart
* rollback to a previous version

== Final Decision

[quote]
____
An Aladin Knowledge Pack is a versioned data product, not a permanently running microservice.
____

This principle is accepted as a foundational architectural rule of the Aladin ecosystem.
