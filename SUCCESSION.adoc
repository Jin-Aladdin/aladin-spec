== Purpose

ADR-0005 states that Knowledge Packs must keep maintaining, validating,
versioning and publishing their knowledge without depending on the continuous
presence of their original creator.

That is an architectural claim. This document is the operational half: who owns
what, what happens when they stop, and how someone who has never seen this
project can take it over.

== Current State

Honest assessment as of the draft `0.1.0` specification series.

== Roles

[cols="1,2,2",options="header"]
|===
| Role
| Responsibility
| Minimum count

| Owner
| Final authority on scope, licensing, releases and repository administration.
| Two, once an organization exists. Currently one.

| Maintainer
| Review, merge, gate changes, quarantine triage.
| One, ideally two.

| Security contact
| Private vulnerability reports, key rotation, compromise response.
| One named person or address.

| Machine identity
| Automated validation, health reporting, candidate pull requests, releases.
| Repository-scoped by default; organization app for cross-repository work.
|===

Roles may overlap in a small project. What must not overlap is the *only* path
to recovery and the person most likely to disappear.

== Recommended Organization Structure

The recommendation, not yet executed:

* move the repositories into a GitHub organization
* at least two owner accounts with independent recovery methods
* separate maintainer and bot permissions
* an organization-owned GitHub App for cross-repository automation
* protected branches or rulesets on `main`
* central workflow templates
* a central sentinel repository
* secrets separated by responsibility

Repository transfer is never performed automatically and requires explicit
approval from the current owner.

== Machine Identity Policy

Preferred order, from ADR-0005:

. the repository-scoped `GITHUB_TOKEN` when its scope suffices
. an organization-owned GitHub App for cross-repository actions
. OpenID Connect for supported external infrastructure
. no personal access token as a permanent foundation

A personal access token belonging to the founder is not an acceptable legacy
architecture. It expires, it is bound to one account, it cannot be handed over
and it grants far more than any single workflow needs.

== Backup and Mirroring

Partly in place.

=== What Exists

`backup-mirror.yml` runs monthly and on dispatch. It produces a git bundle
containing the full history, every branch and every tag, then proves the bundle
is usable by cloning it and comparing the restored tags and HEAD against the
source. A backup nobody restored is a belief, not a backup.

The bundle is a complete repository in one file. `git clone backup.bundle`
reconstructs everything with no network and no hosting provider, which is what
makes it a recovery path rather than a second copy that fails at the same time
as the first.

=== What Is Missing

No independent remote is configured. Set the repository secret
`MIRROR_REMOTE_URL` to a push URL on a different host and the workflow starts
mirroring; without it, the step is skipped and the bundle is still produced.

The mirror push uses `--all --tags` and never `--force` or `--mirror`. A mirror
push propagates deletions and rewrites, so a mistake or a compromise at the
origin would destroy the backup along with it. A backup that can be erased from
the thing it backs up is not a backup.

=== Remaining Targets

Any of these must be substitutable, and none may become mandatory:

* a second git remote on an independent host
* S3-compatible object storage for release bundles
* an independent registry
* an institutional or academic mirror

What must be covered: git history, tags, releases, artifacts, schemas, pack
manifests, provenance data, registry metadata and automation configuration.

Until an independent remote exists, the bundles live on the same provider as
everything else, so GitHub availability remains a real dependency.

== Sentinel

`templates/sentinel-repository/` contains the watcher, ready to copy into its
own repository.

A repository cannot reliably report its own silence: when a platform disables
its scheduled workflows after prolonged inactivity, the heartbeat that would
have noticed is disabled with them, and the repository then looks healthy in
the only way it can still report, by saying nothing. The observer has to live
somewhere the failure does not reach.

The sentinel reads commit age, validation age, update age, release age,
disabled workflows and reachability, and reports. It never edits knowledge
content, never merges and never publishes. The strongest action it can take is
`repository_dispatch`: asking a repository to run a workflow that repository
already declared, which still runs its own gates.

It has the same weakness one level up: it can go quiet too. That is an accepted
and documented limit, mitigated by keeping it small and by having it watch its
own repository.

The template is not yet deployed. Deploying it needs a repository, ideally in
the organization rather than under a personal account, since a sentinel bound
to one person inherits exactly the succession problem it is meant to reduce.

== Handover Procedure

For a maintainer preparing to hand over:

. Name the successor in `MAINTAINERS.adoc` and grant access.
. Confirm the successor can run the *Manual recovery* workflow.
. Confirm the successor can cut a release.
. Transfer or re-create every machine identity under the new owner.
. Rotate every secret. Handover is a rotation event.
. Update this document with the new ownership and the date.
. Leave the old maintainer's access in place for one overlap period, then
  remove it deliberately rather than by expiry.

For a successor taking over cold:

. Read `README.adoc`, then `decisions/`, in order.
. Run the *Manual recovery* workflow with `run-all-gates`.
. Read `automation/health.json` to see what the automation last observed.
. Check the Actions tab for disabled scheduled workflows and re-enable them.
. Review any open `automation-health` issue.
. Do not change gate configuration before you can make the gates pass.

== Abandoned Account

If the founding account becomes unreachable and no organization exists:

. The repository content survives in every clone and every published artifact.
. Fork the most recent complete clone.
. Publish the fork with a clear statement of what happened and which commit it
  continues from.
. Recreate the automation from the repository template and this document.
. Do not silently claim the original identity. Continuity must be visible.

This is a recovery path, not a substitute for creating an organization.

== Disabled Automation

GitHub disables scheduled workflows after prolonged inactivity. This is
expected, not exceptional.

. The heartbeat exists to make the silence visible.
. `automation/health.json` records the last observation and its age.
. The *Manual recovery* workflow restores a known state without local tooling.
. A sentinel repository, once it exists, detects the silence from outside.

A heartbeat reduces risk. It does not guarantee that a hosted CI platform will
run forever, and this document does not pretend otherwise.

== Compromised Automation

. Revoke the affected credential immediately.
. Disable the update and release workflows.
. Review `automation/audit/` for every decision in the affected window.
. Verify published artifact checksums against the release records.
. Recall any artifact that cannot be verified.
. Rotate credentials and re-enable workflows one at a time.
. Record the incident and its resolution.

A recall never deletes history.

== Known Single Points of Failure

Stated plainly, because an unstated risk is an unmanaged one:

. One personal account owns the canonical repository.
. No organization and no second owner exist.
. No independent mirror is configured. Verified backup bundles exist, but they
  are retained on the same provider, so a provider-level loss takes both.
. Knowledge Pack repositories built from the template check out this
  repository for their tooling. The template documents vendoring as the
  mitigation, but the dependency is real until they pin and vendor.
. The sentinel exists as a template and is not deployed, so nothing yet
  observes a repository whose automation went silent.
. Nothing watches the sentinel. That regress has to stop somewhere, and it
  stops here deliberately rather than by oversight.
. The `0.1.0` specification is a draft. Only its schema identifiers are fixed,
  by the tag; nothing about its content is frozen.

Each of these is tracked as a gap rather than described as solved.
