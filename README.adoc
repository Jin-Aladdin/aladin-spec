== Vision

Modern AI systems often depend on knowledge locked inside a specific application, database, cloud provider or model ecosystem.

Aladin separates knowledge from the system that consumes it.

The specification defines portable *Knowledge Packs* that can be:

* inspected by humans
* processed by machines
* validated automatically
* connected to original sources
* updated independently
* versioned reproducibly
* indexed by different retrieval systems
* consumed by local or hosted AI models
* transferred between compatible platforms

The objective is not to create hundreds of permanently running knowledge APIs.

Each knowledge repository is a source project that produces a validated and optimized data artifact. A central gateway, indexer or compatible AI platform can load and serve many Knowledge Packs dynamically.

== What Is a Knowledge Pack?

An Aladin Knowledge Pack is a versioned, machine-readable collection of structured knowledge and supporting metadata.

A pack may contain:

* claims and facts
* source references and provenance
* entities and relationships
* multilingual content
* licensing and usage restrictions
* quality and trust metadata
* compatibility information
* validation results
* checksums and build provenance
* optional search indexes and embedding metadata

A Knowledge Pack is a *data product*, not a permanently running microservice.

[source,text]
----
Knowledge Repository
        │
        │ Validate and build
        ▼
Versioned Knowledge Artifact
        │
        │ Publish
        ▼
Artifact Storage and Registry
        │
        │ Discover and load
        ▼
Global Metadata Index
        │
        │ Retrieve and re-rank
        ▼
Context Builder
        │
        │ Ground
        ▼
AI Model, Agent or Application
----

== Core Principles

=== Portable

Knowledge must not depend on one mandatory language model, database, vector store, cloud platform or proprietary runtime.

=== Verifiable

Important claims should be connected to identifiable sources and provenance metadata.

=== Versioned

Every published Knowledge Pack must have an identifiable version and reproducible artifact metadata.

=== Declarative

Knowledge Packs primarily contain structured data. They must not require their own permanently running application server.

=== Secure by Default

A Knowledge Pack must not execute arbitrary code inside the consuming AI system. Untrusted data must be treated as data, not as executable instructions.

=== Source-Aware

Knowledge should preserve its origin, retrieval time, authorship, licensing and transformation history.

=== Backward-Compatible

New specification versions should provide explicit compatibility rules and migration paths for older Knowledge Packs.

=== Model-Independent

The same pack should be usable with local models, hosted models, retrieval pipelines and agent frameworks.

=== Open and Extensible

The base specification is public and may be implemented by independent tools, organizations and platforms.

=== Reversible

Knowledge Packs must support deprecation, recall, rollback and replacement when information becomes invalid or legally unusable.

== Proposed Architecture

[cols="1,3",options="header"]
|===
| Layer
| Responsibility

| Knowledge Repository
| Stores structured knowledge, source definitions, tests and build configuration.

| Validator
| Checks schemas, provenance, licenses, compatibility and integrity.

| Artifact Builder
| Produces optimized, immutable and versioned artifacts.

| Artifact Storage
| Stores packages, checksums, signatures and historical versions.

| Registry
| Publishes discoverable metadata about available Knowledge Packs.

| Global Metadata Index
| Maps questions, concepts and entities to relevant packages and chunks.

| Retriever
| Retrieves candidates from the most relevant packages.

| Re-Ranker
| Scores candidates by relevance, trust, freshness and source quality.

| Context Builder
| Selects, deduplicates and organizes knowledge within a token budget.

| AI Runtime
| Uses selected knowledge to ground an answer, workflow or agent decision.
|===

== Retrieval Pipeline

A single request may require knowledge from several independent packs.

[source,text]
----
How do I write a Bash script on Linux that starts
PostgreSQL inside a Docker container?
----

This request may involve:

* `aladin-kb-bash`
* `aladin-kb-linux`
* `aladin-kb-docker`
* `aladin-kb-postgresql`

The runtime should not blindly query every available package.

. Analyze the request.
. Detect concepts, entities and task intent.
. Search the global metadata index.
. Select relevant Knowledge Packs.
. Retrieve candidate chunks.
. Apply source, license and freshness filters.
. Re-rank the candidates.
. Remove duplicates and weak matches.
. Detect relevant contradictions.
. Build a token-budgeted context.
. Send grounded context to the selected AI model.

== Trust States

[cols="1,3",options="header"]
|===
| State
| Meaning

| Official
| Maintained or explicitly approved by the official Aladin project.

| Verified
| Passed defined validation, provenance and quality requirements.

| Community
| Published externally without official verification.

| Experimental
| Intended for testing and may contain unstable structures.

| Quarantined
| Temporarily blocked due to security, quality, licensing or integrity concerns.

| Deprecated
| Available for compatibility but no longer recommended.

| Recalled
| Must no longer be loaded by compatible production systems.
|===

== Security Model

Knowledge Packs may originate from untrusted repositories. Compatible implementations should account for:

* arbitrary code execution
* prompt injection inside knowledge content
* malicious metadata
* path traversal
* oversized artifacts and decompression bombs
* poisoned embeddings
* manipulated checksums
* forged provenance
* license laundering
* knowledge poisoning
* unauthorized package replacement

Knowledge Packs are declarative by default. Executable extensions, if ever introduced, must remain outside the core data format and require explicit permission.

== Compatibility and Versioning

The Aladin specification follows Semantic Versioning.

[source,text]
----
MAJOR.MINOR.PATCH
----

[cols="1,3",options="header"]
|===
| Version part
| Meaning

| MAJOR
| Incompatible changes to required structures or behavior.

| MINOR
| Backward-compatible additions and optional capabilities.

| PATCH
| Backward-compatible corrections and clarifications.
|===

The current working version is `0.1.0-draft`. Specification version `1.0.0` has not yet been released.

== Open-Core Boundary

This repository defines the public Knowledge Pack standard. The public standard must remain usable without requiring a proprietary service.

The specification does not require publication of proprietary components such as:

* private ranking algorithms
* commercial orchestration systems
* private model-routing logic
* hosted control planes
* proprietary datasets
* personalization systems
* enterprise integrations

== Validation

The repository contains a reference validator. It requires only Python and the
development dependencies listed in `requirements-dev.txt`.

[source,text]
----
python -m pip install -r requirements-dev.txt
python scripts/validate.py
python -m pytest tests -q
----

The validator checks that every schema is valid JSON Schema draft 2020-12, that
each example manifest validates against `schemas/manifest.schema.json`, that
every record validates against its collection schema, that identifiers are
unique, that declared entry points exist inside the pack and that every cross
reference between records resolves.

In line with ADR-0003 the validator never executes Knowledge Pack content. YAML
is parsed in safe mode, nothing from a pack is imported or evaluated and no
remote URL is fetched during normal validation.

== Development Roadmap

=== Phase 0 — Foundation

* define project terminology
* define public and private boundaries
* document architecture decisions
* establish the canonical knowledge model
* define initial schemas
* establish governance and security policies

=== Phase 1 — Minimal Specification

* create the first manifest schema
* define claims, sources, entities and relationships
* build a minimal example Knowledge Pack
* create a standalone validator

=== Phase 2 — Reference Implementation

* build two real Knowledge Packs
* test artifact generation and registry integration
* test multi-pack retrieval
* test rollback and package recall

=== Phase 3 — Ecosystem

* public package registry
* gateway reference implementation
* SDKs and MCP integration
* community validation process
* automated compatibility tests

=== Phase 4 — Stable Specification

* complete security and licensing reviews
* freeze required schemas
* publish migration guidance
* release specification `1.0.0`

== Current Development Rule

The specification will be designed and tested before large-scale repository generation begins.

The validator, gateway and repository factory must follow the specification. The specification must not be reverse-engineered from an already rigid implementation.

== Contributing

Contribution guidelines are being prepared. Until the first contribution policy is published, architectural proposals may be submitted through GitHub Issues.

Major architectural decisions are documented as Architecture Decision Records in the `decisions/` directory.

== Security

Security issues should not be published as normal public issues.

Until a dedicated private reporting process is available, do not include credentials, personal data, private keys or production secrets in issues, pull requests or examples.
