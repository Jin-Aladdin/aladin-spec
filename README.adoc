[.lead]
An open specification for portable, verifiable and versioned knowledge packs for trusted AI systems.

Aladin defines a common format for packaging structured, source-backed and machine-readable knowledge.

Knowledge Packs can be validated, versioned, distributed and consumed by AI assistants, local language models, retrieval systems, agents and knowledge platforms without requiring a separate permanent API server for every knowledge domain.

[IMPORTANT]

Aladin Spec is currently in Pre-Alpha.

The architecture and data formats are still under active design. No stable "1.0.0" specification has been released.

toc::[]

== Vision

Modern AI systems often depend on knowledge that is locked inside a specific application, database, cloud provider or model ecosystem.

Aladin aims to separate knowledge from the system that consumes it.

The specification defines portable Knowledge Packs that can be:

* inspected by humans
* processed by machines
* validated automatically
* connected to original sources
* updated independently
* versioned reproducibly
* indexed by different retrieval systems
* consumed by local or hosted AI models
* transferred between compatible platforms

The objective is not to create hundreds of permanently running knowledge APIs.

Instead, each knowledge repository acts as a source project that produces a validated and optimized data artifact.

A central gateway, indexer or AI platform can then load and serve many Knowledge Packs dynamically.

== What Is a Knowledge Pack?

An Aladin Knowledge Pack is a versioned, machine-readable collection of structured knowledge and its supporting metadata.

A pack may contain:

* claims and facts
* source references
* provenance records
* entities and relationships
* categories and concepts
* multilingual content
* licensing information
* usage restrictions
* quality indicators
* trust metadata
* compatibility information
* validation results
* artifact checksums
* build information
* optional search indexes
* optional embedding metadata

A Knowledge Pack is a data product, not a permanently running microservice.

[source,text]

Knowledge Repository
│
│ Validate and build
▼
Versioned Knowledge Artifact
│
│ Publish
▼
Artifact Storage and Registry
│
│ Discover and load
▼
Global Metadata Index
│
│ Retrieve
▼
Re-Ranking and Context Building
│
│ Ground
▼
AI Model, Agent or Application

== Why Aladin?

Knowledge used by AI systems should be more than a collection of copied text fragments.

It should be possible to answer questions such as:

* Where did this information come from?
* When was the source last checked?
* Which license applies?
* Is the content still current?
* Is this a verified fact, an interpretation or an unresolved claim?
* Does another trusted source contradict it?
* Which version of the knowledge was used?
* Can the artifact be reproduced?
* Is the package compatible with the current platform?
* Can a faulty package be recalled or rolled back?

Aladin is intended to make these questions part of the data format itself.

== Core Principles

=== Portable

Knowledge must not depend on one mandatory language model, database, vector store, cloud platform or proprietary runtime.

=== Verifiable

Important claims should be connected to identifiable sources and provenance metadata.

=== Versioned

Every published Knowledge Pack must have an identifiable version and reproducible artifact metadata.

=== Declarative

Knowledge Packs primarily contain structured data.

They must not require their own permanently running application server.

=== Secure by Default

A Knowledge Pack must not be able to execute arbitrary code inside the consuming AI system.

Untrusted data must be treated as data, not as executable instructions.

=== Source-Aware

Knowledge should preserve information about origin, retrieval time, authorship, licensing and transformation history.

=== Backward-Compatible

New specification versions should provide explicit compatibility rules and migration paths for older Knowledge Packs.

=== Model-Independent

The same pack should be usable with local models, hosted models, retrieval pipelines and agent frameworks.

=== Open and Extensible

The base specification is public and may be implemented by independent tools, organizations and platforms.

=== Reversible

Knowledge Packs must support deprecation, recall, rollback and replacement when information becomes invalid or legally unusable.

== Proposed System Architecture

The Aladin ecosystem is separated into multiple layers.

[cols="1,3",options="header"]
|===
| Layer
| Responsibility

| Knowledge Repository
| Stores source definitions, structured knowledge, schemas, tests and build configuration.

| Validator
| Checks structure, source metadata, licenses, compatibility and integrity.

| Artifact Builder
| Produces optimized, immutable and versioned Knowledge Pack artifacts.

| Artifact Storage
| Stores released packages, checksums, signatures and historical versions.

| Registry
| Publishes discoverable metadata about available Knowledge Packs.

| Global Metadata Index
| Maps questions, concepts and entities to relevant packages and chunks.

| Retriever
| Retrieves candidate knowledge from the most relevant packages.

| Re-Ranker
| Scores candidate chunks by relevance, trust, freshness and source quality.

| Context Builder
| Selects, deduplicates and organizes knowledge within a defined token budget.

| AI Runtime
| Uses the selected knowledge to ground an answer, workflow or agent decision.
|===

== Retrieval Pipeline

A single user request may require knowledge from several independent packs.

For example:

[source,text]

How do I write a Bash script on Linux that starts
a PostgreSQL database inside a Docker container?

This request may involve:

* "aladin-kb-bash"
* "aladin-kb-linux"
* "aladin-kb-docker"
* "aladin-kb-postgresql"

The runtime should not blindly query every available package.

The proposed retrieval process is:

. Analyze the user request.
. Detect concepts, entities and task intent.
. Search the global metadata index.
. Select the most relevant Knowledge Packs.
. Retrieve candidate chunks.
. Apply source, license and freshness filters.
. Re-rank the candidates.
. Remove duplicates and weak matches.
. Detect relevant contradictions.
. Build a token-budgeted context.
. Send the grounded context to the selected AI model.

[source,text]

Query
│
▼
Intent and Concept Detection
│
▼
Global Metadata Index
│
▼
Relevant Knowledge Packs
│
▼
Hybrid Retrieval
│
▼
Filtering and Re-Ranking
│
▼
Context Builder
│
▼
AI Runtime

== Canonical Knowledge Model

Different specification versions and source formats should be mapped into one internal canonical representation.

[source,text]

Knowledge Pack Spec 1.x ─┐
Knowledge Pack Spec 2.x ─┼──► Canonical Knowledge Model
External Compatible Data ─┘

This approach allows gateways and retrieval systems to support older package versions without spreading version-specific logic throughout the entire platform.

== Source Provenance

A knowledge claim should be traceable to its origin.

A conceptual claim record may include:

[source,json]

{
"id": "docker.volume.persistence.001",
"type": "factual-claim",
"statement": "A Docker volume can persist data beyond the lifecycle of an individual container.",
"language": "en",
"confidence": 0.98,
"verification_status": "source-backed",
"sources": [
"source.docker.volumes.official"
],
"created_at": "2026-07-27T00:00:00Z",
"last_verified_at": "2026-07-27T00:00:00Z"
}

A conceptual source record may include:

[source,json]

{
"id": "source.docker.volumes.official",
"type": "primary-documentation",
"title": "Docker storage documentation",
"publisher": "Docker",
"retrieved_at": "2026-07-27T00:00:00Z",
"content_hash": "sha256:example",
"license_status": "documented",
"authority_score": 0.95
}

These examples are illustrative and are not yet normative.

== Trust Model

The specification is expected to support several package states.

[cols="1,3",options="header"]
|===
| State
| Meaning

| Official
| Maintained or explicitly approved by the official Aladin project.

| Verified
| Passed defined validation, provenance and quality requirements.

| Community
| Published by an external contributor without official verification.

| Experimental
| Intended for testing and may contain unstable structures.

| Quarantined
| Temporarily blocked due to security, quality, licensing or integrity concerns.

| Deprecated
| Still available for compatibility but no longer recommended.

| Recalled
| Must no longer be loaded by compatible production systems.
|===

A future Trust Score may consider:

* source authority
* source freshness
* provenance completeness
* license clarity
* validation coverage
* contradiction handling
* test coverage
* review status
* package history
* maintainer reputation

The Trust Score model must remain explainable and must not replace human judgment in high-risk domains.

== Security Model

Knowledge Packs may originate from untrusted repositories.

Compatible implementations should therefore assume that package content may be malicious, misleading or corrupted.

The specification will define protections for:

* arbitrary code execution
* prompt injection inside knowledge content
* malicious metadata
* path traversal
* oversized artifacts
* decompression bombs
* invalid schemas
* poisoned embeddings
* manipulated checksums
* forged provenance
* license laundering
* knowledge poisoning
* dependency confusion
* unauthorized package replacement

Knowledge Packs should be declarative by default.

Executable extensions, if introduced in the future, must be isolated from the core data format and require explicit permission.

== Artifact Integrity

Released artifacts should be immutable and identifiable.

A release may include:

* package version
* specification version
* build timestamp
* source commit
* source tree hash
* artifact checksum
* builder identity
* build environment
* signature metadata
* dependency inventory
* validation report

A compatible runtime should be able to verify an artifact before activating it.

== Hot Reload and Rollback

A new Knowledge Pack version should not immediately replace an active version.

A safe activation process may follow:

[source,text]

Active Package: 1.4.1
│
▼
Download Candidate: 1.4.2
│
▼
Verify Integrity and Signature
│
▼
Validate Package
│
▼
Build Search Index
│
▼
Run Health Checks
│
▼
Atomic Activation
│
▼
Active Package: 1.4.2

If validation fails, the previous version remains active.

== Compatibility and Versioning

The Aladin specification will follow Semantic Versioning.

[source,text]

MAJOR.MINOR.PATCH

Example:

[source,text]

1.0.0

[cols="1,3",options="header"]
|===
| Version part
| Meaning

| MAJOR
| Incompatible changes to required structures or behavior.

| MINOR
| Backward-compatible additions and new optional capabilities.

| PATCH
| Backward-compatible corrections and clarifications.
|===

The current working version is:

[source,text]

0.1.0-draft

Specification version "1.0.0" has not yet been released.

A Knowledge Pack manifest is expected to declare compatibility information similar to:

[source,yaml]

specification:
name: aladin-knowledge-pack
version: 0.1.0
compatibility:
minimum_runtime: 0.1.0
supported_specification_series:
- "0.x"

This example is non-normative.

== Embedding Independence

Embeddings are derived search artifacts and must not replace the original knowledge data.

A package containing embeddings should describe:

* embedding model
* model version
* vector dimensions
* normalization method
* source content hash
* creation timestamp
* language coverage
* chunking strategy

Compatible systems should be able to regenerate embeddings from the original structured content.

== Multilingual Knowledge

Knowledge Packs may contain multiple languages.

The specification should distinguish between:

* original source language
* translated content
* machine translations
* human-reviewed translations
* locale-specific variations
* language-independent entities
* language-specific claims

A translated claim must remain connected to its original source and transformation history.

== Non-Goals

The Aladin Specification does not define:

* one mandatory language model
* one mandatory vector database
* one mandatory embedding provider
* one mandatory graph database
* one mandatory cloud platform
* one proprietary AI interface
* one required programming language
* autonomous execution of untrusted repository code
* permanent API servers for every Knowledge Pack
* a universal guarantee that all included information is correct

Implementations may choose their own infrastructure as long as they follow the public compatibility and validation requirements.

== Open-Core Boundary

This repository defines the public Knowledge Pack standard.

The specification may be used by open-source and commercial implementations.

The public standard does not require the publication of proprietary components such as:

* private ranking algorithms
* commercial orchestration systems
* private model-routing logic
* hosted control planes
* proprietary datasets
* personalization systems
* enterprise integrations

The public specification must remain usable without requiring access to a proprietary service.

== Current Development Rule

The specification will be designed and tested before large-scale repository generation begins.

This rule exists to prevent:

* incompatible Knowledge Packs
* duplicated formats
* unmaintainable repositories
* premature infrastructure decisions
* hundreds of packages requiring later migration
* accidental lock-in to an untested architecture

The validator, gateway and repository factory must follow the specification.

The specification must not be reverse-engineered from an already rigid implementation.

== Contributing

Contribution guidelines are being prepared.

Until the first contribution policy is published, architectural proposals may be submitted through GitHub Issues.

When proposing a major change, contributors should explain:

* the problem being solved
* the proposed data model
* compatibility implications
* security implications
* migration requirements
* rejected alternatives

Major architectural decisions will be documented as Architecture Decision Records.

== Security

Security issues should not be published as normal public issues.

A dedicated security policy and private reporting process will be added before the first executable reference implementation is released.

Until then, do not include credentials, personal data, private keys or production secrets in issues, pull requests or example files.
